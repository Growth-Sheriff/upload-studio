# Public application tenancy and processing

This branch uses one deployment and one PostgreSQL database. Every shop has a durable Shop row; merchant-owned rows carry its shopId. UploadItem and SupportReply inherit ownership through Upload and SupportTicket. Shopify Session and the HMAC-verified privacy inbox are control-plane exceptions, not customer data discovery endpoints. Session persistence is handled by the shared Prisma adapter in the authentication workstream.

## Trust boundary

The HTTP handler establishes withTenantRequest before Remix dispatches loaders. Verified Shopify admin, app-proxy and webhook authentication bind its store with enterTenantContext. A request cannot rebind to another shop. Worker dispatch uses withTenantContext from trusted, shop-scoped queue payloads. A client body or hostname never establishes tenant identity.

AsyncLocalStorage is deliberately a request-local mutable object: entering a context inside an awaited authentication helper alone does not propagate it into the caller's previously registered continuation. Binding a store established at the HTTP boundary does. Three interleaved requests test this exact boundary.

Prisma queries are lazy thenables. Context wrappers assimilate their returned thenable before leaving the store; otherwise a caller's later await runs middleware outside the authenticated shop. The real database fixture caught this case and now exercises it.

Guarded Prisma injects shopId into reads, aggregates, single/bulk updates, deletes and upserts, including extended unique selectors. Item queries inject upload.shopId; reply queries inject ticket.shopId. Foreign key connects are checked against the owner rather than treating a random global ID as authority. Nested reassignment operations fail closed. New unclassified models fail closed until their ownership rule is supplied. There is no STRICT_TENANT_GUARD=false escape.

Bound Shop reads/writes also receive the current shop's ID. Bootstrap OAuth/session lookup and bounded worker Shop discovery are the allowed control-plane queries. Tenant raw SQL is denied unless called through the reviewed withTenantSql helper; the measurement compare-and-swap and canonical projection SQL include the parent upload's shop_id predicate. Only the exact SELECT 1 health probe is unscoped.

The public identity page and legacy download-by-upload endpoint no longer discover an owner from a global upload ID. Their durable HMAC capability includes both shopId and uploadId and binds the tenant only after verification. Print Ready, Sheet Identity and DPI remain the same three properties; the identity URL carries its capability. Signed object-file URLs already bind an exact object key. File hashes used for upload deduplication/resume remain, while device signatures were removed from short-lived abuse limiting.

## Shared queues and resources

One dedicated Redis DB0 serves all shops. publicRedisUrl rejects inherited tenant DB indices. Queue names are auto-gang-sheet-measure-preflight, auto-gang-sheet-preview-render and auto-gang-sheet-export. Job payloads carry shopId. A distributed atomic sorted-set lease limits each shop to two active upload-processing jobs across the three queues and all replicas. Busy work yields a BullMQ slot for five seconds without consuming a failed attempt; token-specific release is idempotent and expired leases recover from process death. A global large-image lease still protects peak raster memory. This is a concurrency cap, not a promise of strict round-robin ordering.

The old global jobs-per-minute limit was removed: a busy shop's yielded attempts would consume that quota and delay other shops despite the lease. Worker process concurrency defaults to one. Scale separate bounded worker replicas rather than putting high-concurrency decoders beside the web server. Queue-gap reconciliation discovers 50 shops per tick in a rotating cursor, then processes each shop with its owner context and its own upload cursor; it never queries all uploads without an owner.

Whole-job deadlines are cancellable and capped at 15 minutes (measure normally 12, preview 8, export 15). Object downloads have a 120-second deadline covering headers and the complete body, enforce a 1 GiB per-object processing limit and remove partial output. R2 gets the same abort signal as its body pipeline. Image commands kill their Linux process group on deadline/abort, so a killed shell cannot leave convert or Ghostscript running. Child output is bounded to 16 MiB; Linux virtual address space is capped at 3 GiB per process and ImageMagick memory/map/disk/thread budgets are explicit. These are process limits, not a complete job-level cgroup accounting proof; the deployment's separate worker container limits remain necessary.

Late asynchronous continuations cannot begin tenant DB writes after their processing deadline. Already-running database statements still require PostgreSQL statement_timeout at deployment; application cancellation cannot roll back a statement already accepted by PostgreSQL. Generated asset puts re-check the owning upload's privacy stop and shop's immutable erasure marker. Erasing shops reject new ORM/raw tenant writes, but delete operations remain available to privacy processing. Exports use the same normalized shop object prefix as uploads and persist their object key before PUT, so privacy cleanup can find ZIPs after a storage-success/database-completion crash.

The dedicated entry is node --import tsx workers/public-app.worker.ts with PUBLIC_APP_RUNTIME=true and one explicit PUBLIC_WORKER_ROLE: measure, preview, export, billing, privacy or flow. It does not run any tenant deployment/bootstrap script. Operational aggregate queue counters require PUBLIC_OPERATIONS_TOKEN; public /health exposes only database/Redis health.

## Erasure timing and limitations

Full-shop erasure first closes the shop, then drains the longest issued capability before the final object-prefix/database sweep. Upload PUT/part capabilities currently live one hour, longer than processing jobs; a 16-minute drain would permit a late direct storage PUT to recreate an orphan. The privacy workstream uses a 61-minute delay before completing the final sweep. Merely checking a shop before a put cannot remove this storage race. Customer erasure marks affected uploads immediately; old queued/retried upload and export jobs cannot begin processing them.

The application guard is not PostgreSQL RLS. Direct scripts, additional database clients, migrations and SQL helpers must be reviewed separately; production app code and worker clients import the guarded factory. Object authorization is separately enforced by signatures and owner-checked key issuance. This document does not claim a running three-store Shopify installation or peak ImageMagick/cgroup proof.

## Executed local evidence

On 2026-10-09, the focused queue/vector/tenancy/resource suites and three real integration fixtures passed 41 tests; five ImageMagick-dependent override tests were skipped on this Windows host, not counted as proof. The passing tests cover simultaneous three-shop request binding, a caller-injected shop, single and bulk queries, foreign upload connects, signed identity tampering, partial/hanging downloads and headers, size limits, post-deadline write attempts, erasing-shop write closure, token-specific lease release and shared Redis DB0. The lease unit fake explicitly does not prove Redis Lua execution; the separate real integration fixture does.

The Linux timeout mechanism was also executed in a disposable node:22-alpine container using a bundled copy of runImageCommand. A shell started a 30-second sleep child and waited; a 200ms deadline returned in 210ms. The child was a non-running zombie (Z), not a decoder still consuming CPU; the disposable container exited and was removed. An init process in worker containers must reap orphaned children. The generated bundle was removed. This proves process-group cancellation, not an actual large-image memory run.

The real integration run on 2026-10-09 passed all three fixtures: publicTenancy.integration.test.ts, shopWorkerLease.integration.test.ts and prismaSessionStorage.integration.test.ts. The dedicated local PostgreSQL public_app_test database on 127.0.0.1:55439 contained three disposable shops; the guarded client prevented foreign reads, writes, foreign-key connections and writes during erasure. A second Prisma pool restored three shops' tokens/refresh tokens and revoking one left the other sessions intact. Two Redis clients on 127.0.0.1:56389/0 executed the Lua lease script concurrently, enforcing a shared two-job cap and independent capacity for another shop, and recovering an expired fixture lease. Fixtures cleaned their own rows/keys.

The database fixture only accepts PUBLIC_TENANCY_TEST_DATABASE_URL with a public_*_test database and public schema; the Redis fixture only accepts the dedicated loopback test port. Neither falls back to a live DATABASE_URL/REDIS_URL. These prove local middleware, persistence and Redis behavior, not three real Shopify installations. Repeat: PUBLIC_TENANCY_TEST_DATABASE_URL=<isolated test URL> PUBLIC_TENANCY_TEST_REDIS_URL=<isolated Redis URL> npx vitest run app/lib/publicTenancy.integration.test.ts app/lib/shopWorkerLease.integration.test.ts app/lib/prismaSessionStorage.integration.test.ts.
